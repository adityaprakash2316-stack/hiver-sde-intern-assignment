## 1. Problem framing

**What "good" means for AppleSupport**

Apple's public Twitter support is high-volume, brand-sensitive, and mixes:
- Fast, scriptable how-to / troubleshooting questions that can be auto-resolved.
- Hardware, account-security, and billing disputes that require human judgment or physical service.
- Angry, multi-turn, or legally-tinged complaints that must never be auto-replied to with a generic answer.

A trustworthy agent therefore optimizes for:

1. **High precision on "auto-handle"** — false auto-handles are more damaging than false escalations.
2. **Grounded replies** — language and next-steps that actually appear in historical AppleSupport resolutions (not pure LLM hallucination).
3. **Transparent escalation reasons** — every escalate/auto decision must be inspectable.
4. **Low latency & reproducibility** — the system must be runnable offline and produce the same numbers on the golden set.

**What we chose not to build**

- End-to-end fine-tuned seq2seq or LLM generation (expensive, less reproducible for a take-home, harder to debug).
- Full multi-turn dialogue manager / memory.
- Production-grade authentication, rate limiting, or PII redaction pipelines.
- Live Twitter ingestion.
- Automatic ticket creation in an external helpdesk.
- An LLM-as-judge rubric with human-agreement evidence — attempted, but not completed in the time available. See sections 5 and 6.

These were deprioritized so the core claim ("the agent classifies, drafts grounded replies, and escalates safely") could be measured cleanly on real data.

## 2. System overview

```
Customer message
       │
       ▼
┌──────────────────┐
│  Intent classifier│  TF-IDF (1-2 grams) + Logistic Regression, trained on
└────────┬─────────┘  101,276 REAL (customer_message, historical_reply) pairs
         │             extracted from the Kaggle Customer Support on Twitter corpus
         ▼
┌──────────────────┐
│  Retriever        │  Same TF-IDF space → top-k historical (message, reply) pairs
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  Reply drafter    │  Highest-similarity historical reply + light prefix / intent glue
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  Escalation policy│  Rules (anger, security, hardware) + confidence threshold,
└────────┬─────────┘  keyed off the PREDICTED intent (see section 4, finding #1)
         │
         ▼
   {intent, draft, escalate?, reason}
```

The Python FastAPI service owns the above. Spring Boot is a thin, typed API gateway; React is the interactive proof surface.

**Data pipeline note:** the training/retrieval pool (101,276 pairs) uses *weak* intent labels from a 14-category keyword heuristic (`prepare_real_data.py`), not human review — this is an explicit, documented simplification. The 151-example golden evaluation set is hand-labeled by a human against the real message + real historical reply, and is the only source of verified ground truth in this project.

## 3. Results vs baselines

On the **151-example real, hand-labeled golden set** (`data/golden/golden_eval.jsonl` — see `data/golden/LABELING_NOTES.md` for sampling and labeling method):

| System                    | Intent Acc | Macro-F1 | Escalation F1 | Reply proxy |
|---------------------------|------------|----------|----------------|-------------|
| **Our agent**              | 0.728      | 0.174    | 0.000          | 0.408       |
| Trivial (majority class)   | 0.411      | —        | 0.000          | —           |
| Simple keyword rules       | 0.695      | 0.153    | —              | —           |

(Full breakdown in `results/metrics.json` and `results/intent_report.txt`, generated by `python scripts/evaluate.py`.)

**Headline read:** the trained classifier beats the trivial baseline comfortably (0.728 vs 0.411), but only edges out a handful of `if "battery" in text` keyword rules by ~3.3 points (0.728 vs 0.695). Macro-F1 (0.174) is far below accuracy (0.728), which is the first sign something is wrong beneath the surface — see section 5. Escalation F1 is 0.000, meaning the escalation policy did not correctly flag a single true-positive case in this golden set — see section 4, finding #1.

*(Note: a golden-set QC pass during failure analysis caught 4 mislabeled examples — e.g. a CarPlay dark-mode feature request originally mislabeled `account_lock` — which were corrected before this final run. `hardware_failure` and `complaint_escalation` no longer have any examples in the golden set as a result, since their only occurrences were among the corrected rows.)*

## 4. Failure analysis — top 5 modes

**How to reproduce these**: `results/failures.jsonl` (written by `scripts/evaluate.py`) contains every golden example where the predicted intent or escalation decision was wrong, with the real message text. To pull concrete examples for each mode below:
```powershell
python -c "import json; [print(json.dumps(r)) for r in map(json.loads, open('results/failures.jsonl', encoding='utf-8')) if r['true_intent']=='account_lock']"
```
(swap `'account_lock'` for whichever `true_intent` you want examples of).

1. **Escalation fails whenever the underlying intent is misclassified (compounding error)**
   `decide_escalation()` branches on the classifier's *predicted* intent, not the true one. Since the classifier almost never predicts minority classes like `account_lock`, `hardware_failure`, or `billing_refund` (see finding #2), it never reaches the escalation rules tied to those intents — even on messages that genuinely needed escalation. This is why escalation F1 is exactly 0.000 rather than merely low: it's not that the escalation *logic* is wrong in isolation, it's that upstream misclassification silently prevents it from ever firing on the cases that matter most. **[Pull 2-3 real examples with `true_esc=True, pred_esc=False` from `results/failures.jsonl`.]**

2. **Class imbalance collapses recall on every minority-but-real intent**
   `account_lock`, `billing_refund`, `app_store_purchase`, and `feature_request` all scored **0.000 F1** in the golden-set evaluation — despite being real, trainable classes with hundreds of training examples each (e.g. `account_lock` had 623 training examples). (`hardware_failure` and `complaint_escalation` have zero examples in the corrected golden set, so they can't be evaluated here at all — itself a gap worth noting: a 151-example golden set sampled from a skewed real distribution may end up with no coverage at all for some real, important intents.) The training pool is 54% `general_inquiry` and 24% `ios_update_issue`; `class_weight="balanced"` in the logistic regression was not enough to overcome this skew with a purely lexical (TF-IDF) feature space. **[Pull examples where `true_intent` is one of these six from `results/failures.jsonl`.]**

3. **Golden taxonomy exceeds the classifier's trainable label space**
   22 of the 151 golden examples (~15%) use one of 18 custom intents introduced during hand-labeling (e.g. `accessibility_issue`, `keyboard_input_bug`, `warranty_repair`) that the classifier cannot predict by construction — its label space is fixed to the 14 categories from the weak-labeling heuristic. These 22 examples are guaranteed misses regardless of model quality, mechanically capping the ceiling on intent accuracy. This is a genuine scope mismatch between the human-defined taxonomy (which is supposed to emerge from the data, per the assignment) and the training pipeline (which was built before that taxonomy fully existed).

4. **High-confidence errors — the model doesn't know what it doesn't know**
   Smoke-testing during development ("Someone hacked my apple id...", "The screen on my iphone is completely cracked...") returned confidence scores of 0.93-1.00 even on the smaller/rarer intents. Combined with finding #2, this means the confidence-based escalation fallback (`< 0.40 → escalate`) rarely triggers as a safety net, because the model is (over)confident even when wrong.

5. **A cracked-screen message under-escalated until manually caught**
   During smoke testing, "The screen on my iphone is completely cracked after i dropped it" classified correctly as `screen_issue` but did not escalate, because the original escalation rule only checked `hardware_failure` and `account_lock`. This was caught by hand and patched (`screen_issue` added to the rule) rather than being discovered systematically — which itself is a finding: manual smoke-testing surfaced a real gap that the automated golden-set evaluation, run before the fix, would not have isolated as clearly from the noise of findings #1-#3.

## 5. What is misleading about my headline number?

- **72.8% accuracy sounds solid in isolation, but the keyword-rules baseline gets 69.5%.** Nearly all of the "learned" model's apparent skill is really just correctly handling the same 3 dominant classes (`general_inquiry`, `ios_update_issue`, `battery_drain`) that a handful of `if/else` string checks already handle. The accuracy number alone hides how little the ML model is actually contributing beyond that.
- **Macro-F1 (0.174) tells a completely different story than accuracy (0.728).** A reader who only sees the accuracy number would conclude the classifier works well across the board. It doesn't — it works well on 3-4 large classes and fails completely (0.000 F1) on real, meaningfully important classes including `account_lock`, `billing_refund`, `app_store_purchase`, and `feature_request` — exactly the categories where a wrong answer is most costly.
- **Escalation F1 of 0.000 is invisible if you only report intent accuracy.** A stakeholder skimming "72.8% intent accuracy, looks reasonable" would have no idea the escalation system — arguably the actual safety-critical part of this whole assignment — failed to correctly escalate a single true case in the golden set.
- **~15% of the golden set is mechanically unscoreable** (finding #3 above) — the accuracy number is capped below 100% for reasons that have nothing to do with how good the classifier is on the cases it *could* possibly get right.
- **The training data's "true" intent distribution is itself an artifact of the weak-labeling heuristic**, not verified ground truth. 54% of training examples fell into `general_inquiry` largely because the keyword heuristic defaults there whenever nothing else matches — this may overstate how often real AppleSupport traffic is actually generic, and understates true prevalence of specific issues.
- **Reply quality (0.408, unchanged by the golden-set corrections) is measured by a lexical-overlap proxy only.** No LLM-as-judge or human-preference evaluation was completed (see section 6) — this number should not be treated as a real measure of reply helpfulness or correctness, only as a weak, easily-gamed heuristic.

In short: the numbers demonstrate the pipeline runs end-to-end on real data and beats a trivial baseline — they do **not** demonstrate the model has learned much beyond what simple keyword rules already capture, and they actively hide a complete failure of the escalation system on the classes that matter most.

## 6. What I'd do with one more week

1. **Decouple escalation from predicted intent.** Run the hardware/account/billing keyword-and-confidence checks against the raw message text directly, independent of the classifier's intent prediction, so a misclassification doesn't silently suppress an escalation that should have fired. This is the single highest-priority fix given finding #1.
2. **Address class imbalance properly** — oversampling/undersampling, or a two-stage classifier (common-vs-rare intent first, then a specialized model for the rare-but-critical classes: `account_lock`, `billing_refund`, `hardware_failure`).
3. **Reconcile the human-defined intent taxonomy with the trainable label space** — either fold the 18 custom intents back into keyword rules so the classifier can learn them, or explicitly scope the golden set to only the 14 pre-defined categories and treat taxonomy expansion as a separate, second-pass exercise.
4. **Finish the LLM-as-judge + human-agreement evidence.** A working script (`scripts/llm_judge.py`) was built against a free-tier LLM API but not run to completion in the time available — this is the most concrete unfinished piece of the assignment's required deliverables and the first thing to complete.
5. **Get a second labeler on a 30-40 example overlap** with the existing golden set to measure inter-rater agreement on both intent and escalation decisions — the current golden set has no such check (see `LABELING_NOTES.md`).
6. **Consolidate the 19 single-use custom intents** introduced during labeling into a smaller, genuinely recurring set, and re-run labeling on the remaining ~350 unlabeled candidates in `data/golden/candidate_pool.jsonl` to grow the golden set toward the upper end of the assignment's 150-250 range with a settled taxonomy.
7. Replace TF-IDF retrieval with a small sentence-transformer (or BM25 + cross-encoder re-rank) and measure lift on the golden set.
8. Package the whole stack in Docker Compose so "one command" brings up AI service + Spring Boot + UI.

## 7. Decision log (summary)

See `decision_log.md` for the full 14 non-obvious decisions. Highlights:

- Replaced a fully-synthetic data generator with a real-data extraction pipeline partway through, after recognizing a synthetic golden set couldn't survive being asked "how did you build this."
- Golden set (151 real examples) was treated as a first/prototype pass given time constraints — not stratified, not cross-checked by a second labeler, and only 151 of 500 pooled real candidates were labeled.
- Discovered mid-evaluation that the escalation policy's dependence on predicted (not true) intent causes a compounding failure mode — documented rather than silently left in the results.
- LLM-as-judge was scoped as required but not completed; explicitly logged as unfinished rather than glossed over.
