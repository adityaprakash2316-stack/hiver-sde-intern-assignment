# Hiver SDE Intern — AppleSupport AI Agent

**Take-home assignment submission**

> Turn a messy real-world customer-support dataset into a working AI system and *prove* it works.

This repo implements an end-to-end AI support agent for **AppleSupport** — chosen as the highest-volume brand in the public [Customer Support on Twitter](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter) dataset, and the brand most frequently studied in papers that use this corpus.

The agent, given a customer message:

1. **Classifies** it into a 14-intent taxonomy derived from the data.
2. **Retrieves** similar historical resolutions and **drafts a grounded reply** from them.
3. **Decides** auto-handle vs. escalate-to-human, with an explicit, inspectable reason.

**Stack:** a lightweight Python (FastAPI + scikit-learn) service owns the ML logic; a **Spring Boot** backend exposes it as a typed REST API; a **React** frontend provides an interactive demo.

```
Customer message
       │
       ▼
┌────────────────────┐
│  Intent classifier  │  TF-IDF (1-2 grams) + Logistic Regression
└─────────┬───────────┘
          ▼
┌────────────────────┐
│  Retriever          │  Same TF-IDF space → top-k historical (message, reply) pairs
└─────────┬───────────┘
          ▼
┌────────────────────┐
│  Reply drafter      │  Highest-similarity historical reply + light intent-aware framing
└─────────┬───────────┘
          ▼
┌────────────────────┐
│  Escalation policy  │  Rules (anger / security / hardware) + confidence threshold
└─────────┬───────────┘
          ▼
   { intent, draft_reply, should_escalate, escalation_reason, retrieved_examples }
```

## Quick start — reproduce headline results in under 15 minutes

### Prerequisites
- Python 3.10+
- Java 17+ and Maven 3.8+ (a Maven Wrapper is not bundled — install Maven or use Docker, see below)
- Node.js 18+ (only needed for the UI demo, optional for metrics)

### 1. Generate data & train the classifier (~1–2 min)

```bash
cd hiver_sde_intern
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r ai-service/requirements.txt
python scripts/generate_data.py    # writes synthetic-but-realistic AppleSupport data + 200 golden examples
```

> **If `ai-service/models/` already contains a pre-trained `intent_pipeline.joblib`** from a previous run on a different machine, you may see a scikit-learn `InconsistentVersionWarning` on startup, or even an `AttributeError` from `predict_proba`. This means the pickled model was trained with a different scikit-learn version than the one installed. Fix by either:
> - `pip install --upgrade scikit-learn==1.9.1` to match, **or**
> - deleting `ai-service/models/*.joblib` and `ai-service/models/historical.json` so the service retrains fresh on startup.

### 2. Run the evaluation harness (headline numbers)

```bash
python scripts/evaluate.py
# → results/metrics.json   (intent accuracy, macro-F1, escalation F1, baselines)
# → results/failures.jsonl (worst-scoring examples for failure analysis)
# → results/intent_report.txt (per-class precision/recall)
```

### 3. Start the full stack

**Terminal A — AI service (port 8000)**
```bash
cd ai-service
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

**Terminal B — Spring Boot backend (port 8080)**
```bash
cd backend
mvn spring-boot:run
```

**Terminal C — React UI (port 3000)**
```bash
cd frontend
npm install
npm start
```

Open **http://localhost:3000** and try the example messages, or hit the API directly:

```bash
curl http://localhost:8080/api/v1/health
curl -X POST http://localhost:8080/api/v1/support \
  -H "Content-Type: application/json" \
  -d '{"text": "My iPhone 13 battery is draining insanely fast after the latest update."}'
```

### Alternative: Docker Compose

```bash
docker-compose up --build
```
Brings up all three services together (see `docker-compose.yml`, and each service's `Dockerfile`).

## Golden evaluation set

- **Size:** 200 examples · **Location:** `data/golden/golden_eval.jsonl`
- Stratified across all 14 intents (~12 each) plus deliberately hard/ambiguous cases
- Full labeling methodology in `data/golden/LABELING_NOTES.md`:
  - Messages curated to match phrasings/frustration levels observed in the source dataset
  - Ground-truth intent assigned from our bottom-up 14-intent taxonomy
  - Escalation labels: security/account, hardware service, repeated frustration, or explicit escalation requests → escalate; clear self-serve paths → auto-handle
  - Single primary labeler (assignment constraint); ambiguous cases resolved toward "escalate" for safety

## Evaluation harness

```bash
python scripts/evaluate.py
```

Produces:
- Intent accuracy, macro-F1, and per-class precision/recall (`results/intent_report.txt`)
- Escalation precision / recall / F1
- A lightweight reply-quality proxy (token overlap + tone-marker presence vs. the historical gold reply), structured so an **LLM-as-judge** rubric can be dropped in as a drop-in replacement scorer
- Comparison against two baselines: majority-class and keyword-rules
- Worst-scoring examples logged to `results/failures.jsonl` for failure analysis

> LLM-as-judge is left as a clear extension point (set `OPENAI_API_KEY` and extend the scorer) rather than a hard dependency, to keep the pipeline reproducible offline in under 15 minutes.

### What is misleading about the headline number?

(Full version in `REPORT.md` §5 — short version:)

- The golden set is generated from the **same template distribution** as training data, so headline accuracy is an upper bound relative to noisier real Twitter text.
- The **single-label assumption** inflates accuracy vs. a reality where many messages have multiple intents.
- The **reply-quality metric is a proxy** (lexical overlap), not a measure of factual correctness or user satisfaction.
- No **temporal shift** modeling — a 2017-style training distribution will degrade on today's products/issues.
- We deliberately **bias toward escalation**, which looks good on recall but would increase human workload in a real deployment; the real business metric is *safe auto-handle rate*, not raw F1.

## Design choices (short version — see `decision_log.md` for all 12)

- **Brand:** AppleSupport — highest volume + richest public literature in the source dataset.
- **Model:** TF-IDF + Logistic Regression, chosen for speed, full offline reproducibility, and zero external API dependency during evaluation — not for maximum possible accuracy.
- **Retrieval:** same TF-IDF space as classification, keeping similarity scores interpretable without a second embedding model.
- **Escalation:** hybrid — explicit rules (anger/security/hardware keywords) layered on top of classifier confidence, deliberately biased toward escalating when uncertain.
- **Data:** synthetic-but-realistic, generated to match patterns observed in the public Kaggle corpus, rather than redistributing the full 3M-tweet dump (as the assignment encourages).

## Known issues found & fixed during setup

Documented here for transparency since they weren't obvious from the code alone:

1. **scikit-learn version mismatch** — the shipped pre-trained model pickle can be trained with a different scikit-learn version than what's freshly installed via `requirements.txt`'s `>=` pin, causing `predict_proba` to throw `AttributeError: 'LogisticRegression' object has no attribute 'multi_class'`. Fix: pin scikit-learn to match, or delete `ai-service/models/*.joblib` to force a clean retrain.
2. **Backend DTO field-naming mismatch** — the Python AI service returns snake_case JSON (`intent_confidence`, `escalation_reason`, ...), while the original `AgentResponse` Java DTO used camelCase fields with no naming-strategy annotation, so Jackson silently left confidence/reason/retrieved-examples at their default (0.0 / null) values while `intent` (no underscore) happened to still match. Fixed by splitting into two DTOs: `AiServiceResponse` (snake_case, for deserializing the AI service's response) and `AgentResponse` (plain camelCase, for the frontend), with an explicit mapping step in `AgentController`.

## What we deliberately did not build

- Full multi-turn dialogue state tracking
- Fine-tuned LLM generation (cost / reproducibility trade-off for a take-home)
- Real-time Twitter streaming ingestion
- Production-grade auth, rate-limiting, or observability beyond basic health checks

See `REPORT.md` §1 for the reasoning behind each.
